# 森暮 MORI Bistro

前端以原生 HTML、CSS、JavaScript 開發；後端使用 Python Flask 與 SQLite。登入、角色權限、帳號與商品保存由後端處理，送單目前仍為前端模擬。

## 現行 Python 後端與角色權限

安裝：根目錄執行 `npm install` 及 `uv sync --project backend`。以兩個終端分別執行 `npm run dev:backend`、`npm run dev`；後台入口仍為 http://localhost:5173/admin/ 。環境設定與 API 見 [後端說明](../backend/README.md)。

| 操作 | 員工 | 管理員 |
| --- | --- | --- |
| 查看／新增／編輯商品、照片、標籤、顯示狀態 | 可 | 可 |
| 刪除商品 | 不可 | 可 |
| 新增帳號、變更角色／密碼、啟用／停用 | 不可 | 可 |
| 匯入舊瀏覽器菜單（取代整份伺服器菜單） | 不可 | 可 |

此矩陣依使用者確認：「員工可新增、編輯商品，但不能刪除或管理帳號」。畫面依伺服器回傳權限顯示；Python API 每次讀取有效登入、最新角色與啟用狀態，防止只隱藏按鈕卻仍可直接寫入。至少保留一位啟用中的管理員。

登入改為 HttpOnly Cookie 與伺服器 SQLite 工作階段，密碼以 scrypt 雜湊保存；修改操作驗證 CSRF token。登出撤銷登入；角色、密碼、啟用狀態變更後，該帳號既有登入失效。前端不再使用 `sessionStorage` 的舊示範登入。

商品與照片由 SQLite 保存，公開 `/api/menu` 僅回傳顯示中的商品，管理員／員工則可查看全部。前台約每 4 秒在可見分頁更新，操作與核對送單前亦會重新確認菜單。商品寫入使用整份清單加 `revision` 的交易檢查；員工即使手動組合請求移除商品仍會收到 403，版本過期回傳 409。

原本 `localStorage` 菜單保持不變。管理員可按「匯入此瀏覽器舊菜單」並確認取代伺服器菜單；第一次使用 Python 後端會建立九道起始商品，不會未經確認自動覆蓋已有商品。點單與模擬訂單仍保存在瀏覽器，尚未串接廚房 API。

實作決策：比較延續瀏覽器角色模擬、只移轉登入、連同商品寫入移至 Python 三案；選擇第三案，使員工不能刪除商品的限制有伺服器可執行的邊界。以 Flask／SQLite 完成小批次垂直功能，保留現有 UI。未進行真人研究；後續由店家以兩種角色試用商品與帳號操作，若權限範圍不符營運，調整後端權限矩陣與對應測試。

驗證結果：6 項前端單元測試、8 項 Python API 測試、14 項瀏覽器整合測試與建置皆通過。涵蓋員工新增／編輯與禁止刪除、帳號管理、角色變更撤銷登入、最後一位管理員保護、CSRF、登入到期／停用、商品持久化與版本衝突、照片／標籤、舊菜單明確匯入、離線點單保留及既有點餐回歸。已檢視手機員工頁面與帳號編輯畫面。本次僅本機開發與驗證，未推送或部署。

以下段落保留前幾次開發與目錄整理的歷史紀錄；與現行資料保存或登入方式不同時，以本節與後端說明為準。

## 專案目錄與前後端邊界

程式集中於 `frontend/`，未來的 API 後端預留於 `backend/`；管理員介面仍屬於前端，放在 `frontend/src/admin/`。根目錄透過 npm workspace 統一執行指令。前端的 HTML 入口位於 `frontend/index.html` 與 `frontend/admin/index.html`，模組及樣式位於 `frontend/src/`，照片位於 `frontend/public/assets/`，測試位於 `frontend/tests/`，工具位於 `frontend/scripts/`。

建置產物統一輸出至 `frontend/dist/`，截圖與測試結果分別位於 `frontend/artifacts/`、`frontend/test-results/`。這些皆為自動產物，勿直接編輯。`npm run build` 會清理並重建前端輸出目錄。

本次整理採最小範圍的目錄搬移與路徑修正，保留既有開發指令、瀏覽器 `/` 與 `/admin/` 路徑、儲存鍵及功能。沒有新增真正的後端服務，未先選定未來後端框架。`.agents/skills/`、根目錄規範與 README 官方宣告保留原位。未來可將商品儲存與示範登入邏輯替換為對 `backend/` API 的呼叫，再加入後端測試及部署設定。

整理後驗證：根目錄 workspace 指令的 7 項單元測試、12 項瀏覽器流程測試與建置皆通過；靜態入口、模組、樣式與照片路徑可讀取，工具、測試及後端目錄不對外提供。建置產物完整，且不包含舊版根目錄 JavaScript 或開發工具。若搬移前已有開發伺服器，請停止舊程序，再執行 `npm run dev`。

## 啟動

使用 Node.js 22 或更新版本：

```sh
npm install
npm run dev
```

開啟 http://localhost:5173 。請透過 HTTP 啟動，避免直接開 HTML 時 ES modules 受限。

```sh
npm test
npm run test:e2e
npm run build
```

瀏覽器測試使用本機 Microsoft Edge，會自動在 5174 啟動獨立前端伺服器，完成後自動關閉。`frontend/dist/` 為可託管的靜態網站。照片已存入 `frontend/public/assets/`，字型為 Google Fonts，離線時使用系統備援字型。

本次驗證：2 項計算／明細單元測試與 2 項桌面／手機瀏覽器流程測試皆通過，`npm run build` 成功；已檢視 1280px 桌面與 390px 手機截圖。尚未進行真人使用者研究。

## 功能與範圍

- 九道示意餐點、六個分類、名稱搜尋、蔬食篩選。
- 餐點詳情、過敏原、熟度或冰量、數量與備註。
- 桌號、訂單備註、明細增減與移除、10% 服務費。
- 送單前核對與模擬完成畫面。成功後清空購物車，避免重複送單。
- `localStorage` 保留未送點單，`mori-last-order` 保存最後一筆模擬訂單。
- 桌面側欄、手機點單抽屜、鍵盤操作與減少動畫偏好。

品牌、價格、料理與過敏原均為示意，未串接後端、付款或廚房。真正營運前需由店家確認內容並串接送單 API。修改菜單請編輯 `frontend/src/menu.js`；更換視覺請編輯 `frontend/src/styles.css`。

## 後台登入（2026-11-19）

入口 `/admin/`（`/admin` 自動轉址）；靜態建置也包含 `frontend/dist/admin/`。示範帳號為 `admin@mori.demo`，密碼為 `Mori2026!`。

- 登入表單提供必填、電子郵件格式、錯誤帳密提示、密碼顯示切換及 Caps Lock 提示。
- 登入成功顯示管理首頁與現有餐點／分類數量；本次僅完成登入階段，商品增刪尚未實作。
- 以 `sessionStorage` 保留目前分頁的示範登入，重新整理可恢復，8 小時後失效；登出即清除。未儲存密碼，也不影響前台購物車。儲存空間停用時以記憶體維持登入，重新整理後須重新登入。
- 此為純前端模擬，公開的示範帳密及可修改的分頁狀態不構成正式身分驗證或存取控制。正式上線前須接後端登入與伺服器權限驗證。

本次範圍依使用者要求先交付「可登入的後台」。比較共用前台登入彈窗、獨立管理入口、外部身分服務三案後，選擇獨立入口，讓店家管理流程與顧客點餐分開；沿用既有純前端範圍，登入邏輯獨立於 `frontend/src/admin/auth.js`，方便後續替換。真實帳號來源與權限模型尚待確認，未進行店家訪談。由店家試用登入、重新整理與登出；若不能清楚理解登入狀態或示範限制，優先調整提示。自動化驗收涵蓋錯誤登入、工作階段恢復／過期、損壞資料、手機版與原有點餐回歸；不等同正式登入安全驗證。

驗證結果：4 項單元測試與 5 項瀏覽器流程測試通過，靜態建置成功，已檢視後台桌面登入與手機管理首頁截圖。以單一小批次整合登入功能；未推送或部署，既有未追蹤 skills 保持原狀。

## 商品管理

登入 `/admin/` 後選擇「商品管理」，或直接開啟 `/admin/#products`。支援新增、編輯、刪除確認、名稱／描述搜尋與顯示狀態篩選。

- 欄位：照片、名稱、英文名稱、分類、描述、新台幣整數價格（0–999,999）、餐點標籤、過敏原、蔬食標記及菜單顯示開關。既有餐點的熟度／冰量選項在編輯時保留。
- 餐點標籤為選填文字，最多 20 字，提供主廚推薦、人氣必點、招牌特調、無酒精等建議，也可自訂。商品清單顯示現有標籤，編輯時自動帶入；清空後儲存會移除前台照片上的標籤。前台「人氣必點」沿用原有深綠樣式，其餘標籤沿用淺色樣式。

標籤修正驗證：7 項單元測試、11 項瀏覽器流程測試與建置皆通過；涵蓋既有標籤帶入、自訂文字、特殊字元、新商品標籤、清空移除、重整保留及前台跨分頁同步，並檢視手機欄位截圖。此為既有資料欄位的後台操作補齊，使用單一小批次修正。
- 照片支援 JPG、PNG、WebP，原檔上限 5 MB；解碼後縮至最長邊 1200px，以 JPEG 儲存。可於編輯時更換照片，不會修改原始檔案。
- 商品資料與照片儲存於 `localStorage` 的 `mori-catalog-v1`。第一次開啟以原有九道商品作為起點，刪光後保持空菜單。儲存失敗時會明確提示，表單資料保留供重試，上一筆成功資料維持原狀。多分頁修改同商品時，舊表單會被要求重新開啟，避免覆寫新資料。
- 同源、同瀏覽器的前台分頁即時更新；重新整理仍保留商品與照片。隱藏／刪除商品會從未送出點單移除；改價會更新點單金額並提示重新確認，核對中的舊訂單會關閉。
- 此版本仍為純前端、示範登入；商品不會寫回 `frontend/src/menu.js`，不會跨裝置共用。不同 host／port 使用不同資料，清除網站資料會一併移除商品與照片。正式多人管理需另接後端與圖片儲存服務。

設計決策：使用者已明確要求商品照片、描述、價格與菜單呈現。沿用先前已確認的純前端範圍，以「商品列表＋獨立編輯表單」作為小批次交付；相較直接在列表編輯大量欄位或另外開多個頁面，此方式能同時保留照片預覽與清楚的儲存／取消界線。尚未進行店家訪談；驗收以新增有照片商品、修改、停售與前台點餐的完整任務為準。後續由店家實際試用，若不理解顯示狀態或保存範圍，先調整文字及操作提示。

本次驗證：7 項單元測試通過；原有登入／點餐 5 項瀏覽器流程與新增商品管理 5 項流程通過。包含照片格式與容量、無效價格、儲存失敗、多分頁衝突、空菜單、損壞資料及前台同步。靜態建置成功，並檢視桌面與手機商品清單、手機編輯表單截圖。

## 初版雙鑽石決策紀錄

使用者提供：精美餐酒館前端、菜單展示與訂單送出。未知：真實品牌、菜單、用餐型態與營運規則。

Discover／Define：可能需求包含了解店家氛圍、快速尋找料理、確認點單內容。本次暫定店內掃碼情境，核心問題為「如何讓客人愉快挑選料理，並在送出前理解桌號、內容與總額？」尚未訪談客人，以上為設計假設。

Develop：比較品牌介紹頁（氛圍強、點餐距離長）、純文字分類清單（瀏覽快、視覺資訊少）、圖像菜單搭配訂單摘要（內容與點餐並重）。選第三案作為可操作原型。

Deliver：以自動化測試驗證金額、熟度與備註區分、重整保留、分類搜尋、桌號切換及模擬送單。這些只證明軟體行為，不代表用餐體驗已獲驗證。

待執行的使用者測試：由店家邀請 3–5 位客人與外場共同試用，任務為選兩道菜、調整熟度、修改桌號並確認送單，觀察是否能找到餐點、理解服務費與模擬標示。暫定判準為每位皆能完成核心任務且沒有誤解總額；若發生誤解，回到問題定義或調整資訊層級。店家／產品負責人決定是否採用，前端維護者負責修正。此研究尚未執行。
