三週工作可以每天合 main：把供應商替換及姓名遷移拆成獨立相容增量，每個短命 PR 包含審查／排隊，數小時至一天合入。以下假設資料庫及滾動部署，只提供方案，尚未實作或驗證。

| 順序 | 可合併變更／相容性 | 驗證與完成條件 |
| --- | --- | --- |
| 1 | 為舊付款加行為測試，引入 PaymentGateway 抽象，仍只委派舊供應商。 | 授權、扣款、取消、退款、逾時、webhook 語意不變；驗證與最新 main 整合結果。 |
| 2 | Expand：新增 nullable given_name、family_name，保留 customer_name；API／事件加可選欄位，保留舊契約。評估大表 DDL 鎖與耗時。 | 舊程式在新 schema 正常讀寫，新程式能讀舊資料，缺新欄位不阻止付款。 |
| 3 | 部署相容讀寫。新程式優先讀已確認的新欄位，缺值回退舊欄位；舊服務退場前保留 customer_name。以版本／同步狀態偵測舊版修改，使過期新欄位失效或更新。 | 測試新舊服務交錯寫入、競爭與重試，避免舊版改姓名後新版仍讀 stale 新欄位。 |
| 4 | 逐項加入新 adapter、憑證配置、錯誤映射、冪等鍵、webhook 驗簽去重及對帳；切換旗標預設關閉。 | sandbox 合約及故障注入通過；flag off 維持舊路徑。影子驗證限無副作用計算／讀取，不向兩家實際扣款。 |
| 5 | Migrate：限速、分批可重試 backfill，記進度並用條件更新避免覆蓋新修改。完整姓名無法普遍可靠拆分，保留原值，允許缺值、使用者確認或明確領域規則。 | 每批對帳、抽樣、監測缺值／衝突；重跑冪等；無法拆分者有待處理狀態，不能猜完就刪原文。 |
| 6 | 先內部／特定租戶再逐批放量。付款記錄固定 provider 與路由版本，webhook／退款沿原供應商；既有交易保留舊 adapter。 | 成功率、錯誤率、延遲、重複交易、金額／幣別及對帳差異符合事先門檻；觀察及人工核對通過才放大。 |
| 7 | Contract：舊服務與消費者全退場、回退窗口結束，才移除舊欄位。舊 adapter 另等退款／爭議責任結束；清理暫時旗標。 | 無舊讀寫依賴，遷移完整、備份與還原演練通過；有價值的抽象可保留。 |

第一週做基線、expand、相容讀寫；第二週小步加入 adapter 與 backfill；第三週逐步啟用及觀察。Contract 不必硬塞第三週，仍有舊版本或舊交易需求就保留相容層。

若採 dual-write，同一資料庫交易內更新新舊表示；跨儲存則用 durable outbox、冪等消費、對帳補償，明訂衝突權威與部分失敗重試。保留姓名原值與變更紀錄，拆分及重新合成可能有資訊損失，不能宣稱可逆。

付款逾時可能已扣款，先查本地狀態與供應商結果，不可因結果不明就換供應商重試。持久化冪等鍵、狀態機、對帳及人工待確認處理可避免雙重扣款。旗標記 owner、預設、對象、啟用及回退門檻、清理期限；測實際 on/off 組態及重要並存互動。

回退時關新交易路由，讓新交易走舊供應商；已建立的新供應商交易仍按原 provider 查詢、退款或補償。關 flag 不會撤銷扣款或資料寫入。程式可回到仍支援擴充 schema 的相容版本，早期不刪欄位，也不以反向 migration 毀掉資料。主幹紅燈優先修復，短時間不行則 revert 小步程式並保留歷史；不可逆 schema/data 另行復原或 fix-forward。

每步合入前驗證建置、相關單元、合約及必要資料庫整合測試，測最新 main 的合併結果，合入後持續驗證主幹。發布門檻再涵蓋 sandbox、新舊版本並存、故障注入、對帳與回退演練。每個 PR 達成本步相容性及驗證條件即可合入，不必等新供應商整體上線。
