可以每天合 main，但要把「付款供應商替換」與「姓名資料演進」拆成兩條可獨立驗證的工作流。每個 PR 都須保持現行付款可用、對舊服務相容；三週是整體交付期，不是分支存活期。

先固定安全邊界：付款交易只能由一個供應商實際執行。用持久化的交易識別碼、冪等鍵及供應商歸屬記錄，讓重試、webhook、查詢與退款都回到原交易的供應商。逾時或結果未知時先查狀態及對帳，不直接改送另一家，以免重複扣款。

建議依序合併下列小 PR，每個 PR 可在數小時至一天內完成及審查：

1. 補上既有行為的測試、付款成功率／錯誤率／延遲與對帳監測。定義新舊供應商介面、錯誤分類、交易狀態及資料歸屬，先不改執行路徑。
2. 引入付款抽象層，讓舊供應商先透過介面運作。確認外部契約與結果不變，再逐個能力加入新 adapter，例如建立付款、查詢、webhook、取消與退款。
3. 在預設關閉的旗標後接上新供應商。旗標控制新交易路由；已建立的交易持續依持久化歸屬處理。影子比較只比較無副作用的計算或沙盒操作，不能把正式扣款同時送兩家。
4. 姓名資料採 expand → migrate → contract：先新增可空的 given_name、family_name，保留 customer_name 與舊 API。新版本支援新欄位並有明確讀取優先順序；不要直接 rename/drop。
5. 訂定相容期間的寫入規則。新服務寫新欄位時同步更新舊表示；舊服務只更新 customer_name 時也須能被捕捉與處理。可使用資料層相容邏輯、變更事件或可觀察的同步工作，但要明確定義權威來源、版本判斷、重試與衝突規則，避免把較新的姓名覆蓋掉。
6. 分批執行可重跑的回填，帶進度與失敗紀錄。姓名無法可靠以空格切分，需保留原值、支援單名與不同姓名順序；無法判定時保留空值／待確認狀態，不臆造 family_name。
7. 逐一遷移讀寫端與 API 消費者。舊新版並存期間測試所有支援的服務與 schema 組合。確定舊寫入者、舊讀取者與可回退版本都退出後，另開清理 PR 移除相容程式及舊欄位，不必硬在三週內做完。

這種介面演進以擴充、遷移、收斂分開發布，降低一次改名對既有消費者的影響。[Parallel Change](https://martinfowler.com/bliki/ParallelChange.html?collections=null)

三週可以這樣安排：第一週完成行為基準、抽象層、schema 擴充及舊路徑驗證；第二週完成新 adapter、混版測試與回填，開始受控試用；第三週按小流量、部分客戶、較大流量逐步切換。每步是否前進，以驗證結果決定，不以日期硬推。

驗證至少包括：

- 主線必要檢查：單元測試、API 契約、舊新服務對同一 schema 的讀寫、migration 重跑，以及回填與即時更新競態。
- 付款整合：沙盒成功／拒絕／逾時／結果未知、重複與亂序 webhook、同交易重試、退款、供應商簽章與金額／幣別正確性。
- 上線檢查：新舊供應商分別監測成功率、未知狀態、重複交易、錯帳、延遲；每階段抽樣核對內部帳與供應商帳。先訂停止條件，例如任何重複扣款或未解釋帳差即停止擴量。

回退時，先關新交易旗標，讓後續新交易回到舊供應商；已送往新供應商的交易仍由新路徑完成查詢、webhook、退款與對帳。不能把關旗標當成取消已發生的金流。保留新 adapter 與必要憑證直到其交易生命週期結束。

資料回退優先回退應用程式並保留相容 schema。舊版本必須能讀到仍同步維護的 customer_name；若已發生資料不一致，先停有問題的寫入、修復及核對，再恢復流量。不要靠刪新欄位或反跑破壞性 migration 回復。清理舊欄位前另做備份與恢復演練，並確認原始姓名不會因格式轉換而遺失。
