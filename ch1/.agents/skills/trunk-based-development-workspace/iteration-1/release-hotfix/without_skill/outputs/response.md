先處理 1.8 的帳務風險，但不要整條 release 分支 merge 回 main，也不要刪除保護規則。main 已是 2.0，整枝回併可能夾帶舊版專用設定與其他差異，無法證明帳務修正對 2.0 正確；移除保護也會讓無關變更取得捷徑。

一般做法是先在主線重現、加測試修正，再選取修正回補 release。[TBD 的發布分支建議](https://trunkbaseddevelopment.com/branch-for-release/) 但這次在 main 無法重現，可以有記錄地採 1.8 優先修復；不能為了遵守方向而延誤止血，也不能因此忽略其他版本。

緊急流程：

1. 指定事故負責人、修正者與獨立審查者，記錄受影響版本、交易範圍、重現資料及目前生產部署的提交。若風險持續，先暫停受影響的帳務功能或採已驗證的營運止血方式，保存稽核與對帳資料。
2. 在隔離環境用 1.8 生產相同設定與代表性資料重現，補一個修正前會失敗的回歸測試。調查 main 無法重現是已修正、程式路徑改變、設定或資料差異，還是測試條件不足；不能直接判定 2.0 安全。
3. 從 release/1.8 的正確基準建立短期 hotfix，僅包含回歸測試與最小修正，提 PR 到 release/1.8。保留必要 CI、獨立審查及稽核；加速可透過優先排隊、立即審查與聚焦測試，完整相關回歸仍須完成。
4. 驗證金額精度、捨入、幣別、退款、重試及資料相容等與根因相關的路徑，並測試升級與回退。如果需要資料修復，另做可稽核、可重跑的修復方案，先預覽影響與對帳，避免把資料修補藏進程式部署。
5. 以通過 CI 的不可變產物發布 1.8 修補版，先小範圍驗證，監測帳務指標與對帳結果。保留上一版產物及回退步驟；程式回退不會自動撤銷已寫入的帳務資料，需另外處理與核對。
6. 同步為 release/1.9 與 main 建立追蹤事項：逐一評估根因與不變條件。若適用，以獨立 PR cherry-pick 最小提交，衝突時按版本語意移植並在目標版本重跑測試；不要使用整枝 merge 搬運修正。
7. 如果 main 已因其他改動消除根因，補能守住相同行為的回歸測試或相應驗證，記錄相關提交及無需程式修正的理由。1.9 也要提供修正或不受影響的證據，不能只因未接獲回報就跳過。

如果既有正式事故流程提供限時緊急例外，可依該流程由指定人員啟用最小範圍權限，保留審查、檢查與操作紀錄並立即撤回；主管一句「加速」不足以成為永久刪除保護的理由。若沒有現成例外，就讓事故負責人協調快速完成原有關卡。

結案條件是：1.8 已部署並完成對帳，1.9 與 2.0 各有修補或不受影響的證據，資料修復與後續監測有人負責，且所有臨時權限已撤回。以上是處理方案，未執行 Git 寫入。
