你們目前不算 TBD，比較接近有長期 develop 的 Gitflow。每天把 develop 拉進 feature branch，只縮短「取得別人變更」的間隔；兩週後才把自己的成果交回共同主線，仍有兩週的整合風險。PR 等三天，也使每日整合難以落實。每月發布本身不妨礙 TBD：整合、部署與對使用者啟用功能，可以是不同節奏。[TBD 說明](https://trunkbaseddevelopment.com/)

四週計畫如下。以下數字是團隊可調整的初始目標，不是 TBD 的認證門檻。

| 週次 | 實際工作 | 驗收依據 |
|---|---|---|
| 第 1 週 | 盤點所有未合併功能、發布與 CI 依賴，決定未來唯一整合主線為 main。先確認 main/develop 差異，再排定既有工作移入的順序。建立分支年齡、PR 等待與 CI 時間的基準；八人輪值審查，約定工作時段數小時內給首次回覆。 | 有主線切換清單與負責人；每個兩週功能能提出可獨立驗證的小切片。 |
| 第 2 週 | 選兩人試行：把新工作切成半天至一天的小 PR，未完功能放在預設關閉的旗標或抽象層後。拆出快速必要檢查，平行化、快取與分片測試；完整 40 分鐘套件仍持續跑。 | 試行者每日把可用成果合入選定主線；快速回饋目標約 10 分鐘，完整測試失敗有即時負責人。 |
| 第 3 週 | 全員轉向 main 開始新工作；既有 feature branch 逐片消化，避免一次大合併。停止新增以 develop 為目的地的功能。採 PR 與必要檢查保護主線，必要時用合併佇列驗證整合後結果。 | 分支多在一天內結束，例外可見且有拆解方案；主線紅燈優先修復或回退。 |
| 第 4 週 | 完成 develop 上剩餘差異與管線切換後，將其封存。演練關旗標、回退與每月發布；用主線的已驗證提交或標籤建立發布產物，需要穩定期才晚開 release branch。 | 新開發只有一條共享主線；觀察每日整合比例、分支年齡、審查等待、CI 回饋與失敗恢復時間。 |

不要只是把 develop 改名成 main；核心是讓每個人持續把小而可驗證的變更交回共享主線。切換時若仍有不可安全合入的大功能，先拆解、隔離並追蹤，不以刪分支作為進度。

保留每月發布即可。旗標應有負責人、到期日與兩種狀態的測試，功能全面推出後清除。若四週後仍普遍存在兩週分支或三天 PR 等待，代表轉型尚未完成，應先處理工作切分與審查容量。

以上僅為流程建議，未修改 repository。
