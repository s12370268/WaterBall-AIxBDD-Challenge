# Double Diamond Principle

協助使用者以證據理解值得解決的問題，再比較與驗證解法。預設繁體中文，依使用者語言切換。採用 Design Council 的框架；下列證據表、轉階條件與模板是本 skill 的實務操作化，不是官方認證規範。

## 先選擇工作深度

1. 從現有對話擷取目標、受影響的人、情境、已有證據、限制與決策需求。不要重問已知資訊。
2. 判斷當前階段，說明理由。明確區分「現在執行的階段」與「後續規劃」，沒有研究資料時不要宣稱四階段已完成。
3. 使用者要快答時，提供四階段各一至兩項要點與一個下一步；完整任務則採下方流程。只要求某一階段時，聚焦該階段並簡查它所依賴的前提。
4. 缺少會改變決策的重要資訊時，一次問最多三個高價值問題；同時整理可推進的內容。若使用者要求不要反問，就標示假設，產出暫定分析與補證據計畫。
5. 若是已充分定義的執行任務，沿用其決策與限制；用最小必要的檢查協助執行，不強迫重啟整個雙鑽石。

需要概念解釋、來源或歷史時讀 [references/research.md](references/research.md)；需要研究方法、工作坊或複製範本時讀 [references/playbook.md](references/playbook.md)。這些相對路徑均從本 skill 目錄解析。

## 帶有連結或文獻的研究任務

使用者指定連結並要求研究時，先讀完整主文，再沿該網站與主題直接相關的連結查閱方法、背景、案例與延伸框架。視需要補查外部第一手來源；不要只用搜尋摘要代替閱讀。遇到無法讀取的頁面或附件，註明缺口，不假稱已讀。

將研究整理為「關鍵字、方法論、執行步驟、規則、適用條件、例外與限制」，逐項保留可核對的來源名稱、原始網址、章節或 PDF 頁碼（可得時）及查閱日期。記錄從指定頁走到延伸頁的關係；明確區分原文主張、跨來源整合及本次提出的實務建議。來源相互矛盾時保留差異與語境，不自行抹平成單一結論。

## 貫穿全程的做法

- 以受影響的人為起點，納入使用者、第一線人員、被排除或有不同需求的人。網路資料提供背景，不能代替實際參與者的經驗。
- 用可讀表格、旅程或簡圖協助形成共同理解，附文字說明，避免只靠顏色傳達。
- 把受影響者與跨職能夥伴的共創安排寫入計畫；AI 提議不等於已與人共創。
- 先做低成本學習，再依結果改進；新證據可以讓任何階段回到前面，Discover 也可以用原型探索問題。
- 建立證據鏈：`資料／觀察 → 洞察 → 問題定義 → 方案 → 測試 → 決策`。必要時用 E1、I1、P1 等編號連結。
- 將內容標示為「使用者提供」「外部來源」「推論」「待驗證假設」「未知」。使用者陳述未經獨立查證時也要保留其來源性質。記下資料時間、樣本及適用情境；區分已知指標值與建議門檻。
- 不編造訪談、引言、問卷結果、測試數字或參與者。虛構範例標成示意，不能作為研究發現。
- 存在矛盾時保留反例，調查分群、時段、渠道與研究偏差；不可用多數票抹去少數但嚴重的需求。

## 第一個鑽石：探索並聚焦問題

### Discover｜探索，發散

目的：了解情境與需求，檢查最初的問題框架。

1. 將「想要的功能」拆成預期結果與待查證因果。例如「增加聊天機器人」先記為候選方案，追問它要改善誰的哪個任務。
2. 整理現有資料與盲點，建立簡短證據表：內容、來源、類型、限制、待查證事項。
3. 規劃適合情境的研究：訪談／觀察實際行為、分析既有使用資料、描繪旅程及接觸點。選擇對象涵蓋成功者、失敗者、未採用者或第一線；按問題與資源說明選樣理由。
4. 列出數個可競爭的解釋與能推翻它們的證據。沒有一手資料時，交付研究提綱與暫定假說。

產出：受影響者與情境、證據／未知表、競爭解釋、最小研究計畫。

轉階判斷：能否用可追溯資料描述某群人在某情境的需求？若仍只有猜測，保留暫定框架，先補最有決策價值的證據。

### Define｜定義，收斂

目的：從發現中選出值得處理的挑戰。

1. 將觀察依需求或障礙分組，區分症狀、可能機制與已證實因果。每個洞察附來源與反例。
2. 比較候選問題的使用者影響、證據強度、可介入程度與限制；說明取捨，而非使用虛構的精確分數。
3. 撰寫問題陳述：`[誰] 在 [情境] 要達成 [任務／需要]，遇到 [障礙]，造成 [影響]；依據是 [證據]，尚待確認 [未知]。`
4. 轉成 How Might We（我們可以如何……）問題，保留不同解法空間；不要把指定功能偷放進問題定義。
5. 寫下範圍、限制、成功結果、基準值與觀察期間。未知基準寫「待量測」；提議的目標寫「暫定」。

產出：有證據鏈的問題定義、HMW、設計簡報與成功判準。

轉階判斷：問題是否具體、值得處理、未鎖死解法，且能用結果衡量？證據不足時將定義標為暫定，說明優先補證據或並行探索的理由。

## 第二個鑽石：探索並驗證解法

### Develop｜發展，發散

目的：為同一挑戰建立不同機制的可比較解法。

1. 一般提出至少三個實質不同方向，依情境涵蓋流程、內容、服務或技術介入；若範圍限制使其不合理，解釋限制。不要把同一功能的配色或命名算成不同方案。
2. 設計跨職能與受影響者共創活動。若尚未進行，明確寫成計畫。
3. 比較每案的需求連結、預期機制、價值、可行性、成本、包容性、風險與關鍵假設。權重應由情境或使用者決定；無資料時用定性比較。
4. 選最具學習價值的低擬真原型，例如紙本流程、角色扮演、可點擊介面或人工服務。指出原型驗證什麼、無法驗證什麼。

產出：多方案比較、選案理由、關鍵假設及原型／共創計畫。

轉階判斷：是否比較過合理替代方案，且最重要的未知能透過小規模測試降低？避免直接把最熟悉的功能當成定案。

### Deliver｜交付，收斂並持續學習

目的：測試、淘汰、改進方案，安排後續運作與回饋。

1. 在看結果之前寫實驗卡：假設、對象、招募方式、任務／原型、比較基準、觀察指標、期間、暫定門檻、停止條件與負責角色。
2. 按情境同時考慮使用者結果、可行性／營運成本及副作用或公平性護欄。不要把功能上線等同於需求已被滿足。
3. 明列決策規則：什麼結果支持繼續／擴大、修改再測、淘汰或回到 Define／Discover。小樣本質性研究只能支持相應範圍的學習，不能推稱統計代表性或因果證明。
4. 有實際結果時依證據做決策；沒有結果時只交付測試計畫，標示尚未驗證。再規劃分階段推行、交接、監測、回饋管道與下一次檢視。
5. 指出誰能做決策、誰維運及如何支持實驗學習；未知負責人使用角色占位，不杜撰姓名。

產出：實驗卡、決策規則與紀錄、交付／回饋計畫。

## 複雜系統與使用者已鎖定方案

- 跨組織、氣候或公共服務問題，補畫利害關係、權力、依賴、回饋與可能外部影響。使用官方 Systemic Design Framework 作延伸時，說明其 Explore／Reframe／Create／Catalyse 與本流程不同，不混稱原始四階段。
- 使用者已決定某方案時，把它視為真實限制並協助驗證。提出可在限制內比較的版本或介入方式；不要以流程為由阻擋已授權工作。
- 時間有限時縮小研究與原型範圍，保留事實與假設的分界，以及至少一項能推翻提案的測試。

## 回覆結構

依要求調整篇幅；完整分析採下列結構，單階段或快答可合併：

1. **目前判斷**：當前階段、要做的決策、已知限制。
2. **證據與缺口**：來源、推論、假設、未知。
3. **Discover／Define**：發散的解釋、收斂理由、暫定或已支持的問題與 HMW。
4. **Develop**：不同方案及其假設、取捨與選案理由。
5. **Deliver**：實驗卡、結果判讀規則、回饋與回退路徑。
6. **下一步**：最有價值的一至三項行動、負責角色與預期產物。

若只是解釋理論，回答概念、非線性、原則與一個簡例即可，不擴成虛構專案報告。需要引用時連結實際讀過的來源；基本流程可離線使用，有最新外部事實需求再查網路。

## 交付前自查

- 是否真的出現兩次發散與收斂，而不只有四個標題？
- 是否把問題證據與方案偏好分開，並保留反例？
- 是否誠實區分規劃與已執行研究、暫定判斷與已驗證結果？
- 是否有可比較方案、可操作測試及結果驅動的回退條件？
- 是否交代參與者、共創／包容性與決策／維運角色？
- 下一步是否符合使用者的時間與資料限制？
